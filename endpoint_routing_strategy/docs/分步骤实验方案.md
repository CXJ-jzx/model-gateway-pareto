# Model × Endpoint 路由系统分步骤实验方案（路线图）

本文件包含尚未实施的完整调度方案，不代表当前已完成全部功能。当前目录和运行入口见 [项目说明](../README.md)，当前选择与失败反馈实现见 [选择实验说明](../experiments/selection/README.md)。2026-10-06 已新增独立的 [轻量容量压力判断](繁忙判断说明.md)，尚未接入速度优先和队列；延迟队列、真实HTTP和容量原子预占尚未实现。

## 0. 文档说明

| 项目        | 内容                                             |
| --------- | ---------------------------------------------- |
| 实验对象      | 模型已经确定后，从能够提供该模型的 Endpoint 中进行选择与调度            |
| 当前重点      | 数据清洗、SLO、模拟优先级、Pareto 路由、繁忙判断和 Endpoint 环境模拟   |
| 可 Mock 模块 | 重型请求分类器、延迟调度器及暂未实现的外部服务                        |

| 实验性质      | 离线回放与离散事件模拟；最终上线前仍需 Shadow Traffic 或小流量 A/B 验证 |

本文档的目的不是一次性写死完整系统，而是先固定数据契约和模块边界，再按阶段替换 Mock、校准参数和验证策略。

### 当前实施范围（2026-10-04）

按最新要求，本阶段只实现我们的即时Endpoint选择策略：P3的请求感知SLO/Pareto/评分，以及P5中的硬容量投影检查。采用可配置请求与固定状态快照验证规则，调用正式 `RoutingEngine.route_request()`；不接入本方案后文的对照策略，不搭建复杂Endpoint模拟器。

软繁忙状态机、延迟队列、容量原子预占和真实执行闭环仍是后续工作。已补充单请求失败反馈、冷却与安全切换，但不发送HTTP。无候选返回分类原因给调用方，不假装已实现等待或降级。当前实验检查约束、公式、重复一致性和开销，只证明按设计选择，不证明相对其他策略的真实效果优势。实现与命令见 [选择策略实验说明](../experiments/selection/README.md)。

## 1. 实验需要回答的问题

1. 历史日志能否被清洗成时间语义统一、字段可追溯且不存在未来信息泄漏的数据。
2. 原日志没有 SLO、优先级和重型类别时，能否用可配置、可复现的方法补充这些信息。
3. 近期窗口、指数衰减和历史先验能否稳定估计 Endpoint 当前性能，并及时感知性能变化。
4. SLO、Pareto Frontier 和线性选择函数能否做出符合成本与性能偏好的可解释选择。
5. 繁忙算法能否根据 RPM、TPM、并发、排队、延迟和错误率判断每个模型—Endpoint组合的状态。
6. Endpoint 模拟器能否形成闭环：一次路由选择改变负载，执行结果再影响后续选择。
7. 优先级、重型请求信息和延迟调度能否提高关键请求的 SLO 达标率，同时避免长请求和低优先级请求饥饿。
8. 完整策略相比 Random、Round Robin、Cheapest、Fastest、Least Loaded 等基线是否获得更合理的 SLO、成本、成功率和尾延迟平衡。
9. 完整决策链路的路由开销是否可接受，主要耗时和内存来自哪里。

## 2. 实验边界和设计原则

### 2.1 实验边界

- 请求到达时，模型已经确定，本实验不负责模型选择。
- 通过 model_id 索引候选 Endpoint，不扫描全部模型和 Endpoint 配置。
- RPM、TPM、最大并发和当前使用量按模型—Endpoint组合维护。
- Endpoint 整体状态只表达全局健康、网络故障或维护状态，不替代模型级容量。
- 流式与非流式性能窗口严格分开：
  - 非流式主要使用 E2E；
  - 流式主要使用 TTFT 和 TPOT。
- 历史日志只记录旧策略实际选择的 Endpoint，没有未选 Endpoint 的反事实结果。因此历史回放可以验证数据处理和状态估计，但不能单独证明新策略优于旧策略。

### 2.2 设计原则

1. **原始日志只读**：新增字段写入增强数据，不覆盖历史事实。
2. **禁止未来信息泄漏**：时间 t 的决策只能使用 finished_at 不晚于 t 的历史结果。
3. **调度与选路解耦**：
   - 调度器决定哪个请求先执行；
   - 路由器决定该请求选择哪个 Endpoint。
4. **统一选路逻辑**：立即请求和延迟出队请求最终进入同一个 SLO、Pareto 和评分选择器。
5. **高优先级不突破硬限制**：高优先级可以跳过软等待或使用预留容量，但不能突破健康、Cooldown、RPM、TPM和并发限制。
6. **繁忙状态按组合计算**：繁忙不是系统级单一布尔值，而是每个模型—Endpoint组合的状态。
7. **配置驱动**：窗口、半衰期、SLO、优先级比例、阈值、等待时间和评分权重不写死在代码中。
8. **可复现**：每次实验保存 seed、数据版本、配置版本和代码版本。
9. **逐阶段验收**：某阶段未达到通过条件时，不进入依赖它的下一阶段。
10. **热路径不画图**：在线决策只保存 Pareto 数据，SVG 和报告在实验结束后离线生成。

## 3. 建议的完整闭环

```text
历史日志
  ↓
清洗与标准化
  ↓
补充 SLO、优先级、重型类别、预计输出 Token
  ↓
按时间产生请求事件
  ↓
请求画像与特征提取
  ↓
model_id → 候选 Endpoint
  ↓
硬过滤：模型支持、启用、健康、Cooldown、硬容量
  ↓
逐 Endpoint 计算 projected load、busy state、headroom
  ↓
有可立即执行 Endpoint？
  ├─ 是 → 统一 Endpoint 选择器
  └─ 否 → 延迟调度队列 → 到期或容量释放 → 统一 Endpoint 选择器
                                         ↓
                           SLO可行性 → Pareto → 线性评分
                                         ↓
                              原子校验并预占容量
                                         ↓
                              Endpoint 模拟或真实执行
                                         ↓
                  更新并发、RPM/TPM、性能窗口、质量和健康
                                         ↓
                                 形成下一次决策状态
```

硬过滤与繁忙的边界必须明确：

- 硬过滤表示不能发送，例如不支持模型、禁用、不健康、Cooldown或预计超过硬容量。
- 繁忙表示尚未超过硬限制，但负载、排队、延迟或错误压力已经偏高。

## 4. 统一数据契约

实验开始前先固定数据结构。后续真实模块与 Mock 模块使用相同接口。

当前数据处理实现明确区分三个阶段：IncomingRequest表示请求刚到达时的输入；Gateway画像表示补充SLO、优先级、轻重与紧急程度后的调度输入；CanonicalRequest表示执行后的规范事实。下面的字段表是实验信息总览，不能把执行后字段直接传给路由器。实际到达时的输入/输出Token预测分别使用predicted_input_tokens和predicted_output_tokens；旧日志中的实际用量不等于预测。具体实现、字段来源和执行命令见[数据处理说明](../data/README.md)。

## 5. 数据构建方案

### 5.1 原始数据保护

- 原始日志目录只读。
- 清洗结果写入 experiments 下的派生数据目录。
- 派生记录保留源文件、源行号或源 request_id。
- 所有填补字段记录 source 或 is_imputed。

### 5.2 时间语义

```text
arrival_time       请求进入网关
sent_at            请求真正发送给 Endpoint
first_token_at     收到第一个输出 Token
finished_at        请求完成或失败
```

指标统一定义：

```text
E2E  = finished_at - sent_at
TTFT = first_token_at - sent_at
TPOT = (finished_at - first_token_at) / max(output_tokens - 1, 1)
```

如果源日志中的首 Token 字段是相对时间，必须在清洗层转换，后续模块不再猜测字段语义。

### 5.3 清洗规则

至少检查：

- request_id、model_id、endpoint_id 缺失；
- 时间无法解析或时间顺序错误；
- Token 小于零；
- 流式成功请求缺少首 Token 时间；
- 成功请求缺少完成时间；
- request 或 attempt 重复；
- 重试无法归属原请求；
- 单位或数量级明显异常；
- Endpoint 配置不包含该模型；
- 价格币种未统一；
- 价格档无法确定。

异常记录不应默认全部删除，先分类：

- drop：无法用于任何分析；
- retain_for_quality：只用于质量和错误率；
- retain_for_performance：可用于性能窗口；
- impute：允许估算缺失字段。

### 5.4 时间切分

推荐配置化地按时间切分：

| 数据段 | 建议比例 | 用途                   |
| --- | ----:| -------------------- |
| 训练段 | 60%  | Endpoint分布校准和历史先验    |
| 校准段 | 20%  | 窗口、半衰期、繁忙阈值和SLO可行性调参 |
| 测试段 | 20%  | 最终策略对照               |

样本不足的模型可以跳过，但必须记录原因。

### 5.5 请求增强

增强数据至少包含：

```text
request_id
base_priority
slo_profile_id
deadline
max_wait_ms
task_type
predicted_output_tokens
predicted_heavy_type
heavy_confidence
generation_rule_version
random_seed
```

增强逻辑只能使用请求到达前的信息，不能使用实际 Endpoint、实际延迟或实际输出 Token。

## 6. SLO、优先级和重型标签

### 6.1 SLO设计步骤

1. 从健康、低负载、成功请求中构造能力基线。
2. 按 model_id、stream_type、请求规模区间统计 P50、P90、P95、P99。
3. 用历史分布检查目标是否可实现，但最终 SLO 仍是外部配置，而不是从同一次结果反推。
4. 为高、普通、低优先级分别配置 SLO 和最大等待时间。
5. 检查每个 SLO Profile 是否至少存在理论可满足的 Endpoint。
6. 为“没有 Endpoint 满足 SLO”配置明确 fallback。

流式请求必须分别检查 TTFT 和 TPOT。最终评分可以用 η 合并，但不能让合并值掩盖某一个指标已经严重违约。

### 6.2 优先级模拟

基础场景可从以下比例开始：

```text
high   10%
normal 70%
low    20%
```

比例是实验配置。优先级由 request_id 与 seed 的稳定哈希生成，保证重复运行一致。

至少构造：

1. 优先级与请求大小独立；
2. 高优先级包含更多重型或流式请求。

禁止根据请求最终是否超时反向设置优先级。

### 6.3 重型类别

| 类别                   | 路由前信息           | 构造方式                       |
| -------------------- | --------------- | -------------------------- |
| input-heavy          | input_tokens 已知 | 按模型分位数或上下文占比               |
| output-heavy         | 实际输出未知          | 使用 predicted_output_tokens |
| classification-heavy | 任务算力特征          | 根据 task_type 或 Mock 分类器    |
| normal               | 不满足上述条件         | 默认类别                       |

阈值按模型配置，不建议所有模型共用一个绝对 Token 阈值。

实验同时提供：

- Oracle：预测等于标签，用于测量算法上限；
- Noisy：按混淆矩阵制造误差，用于鲁棒性实验；
- Baseline：全部作为 normal，用于消融。

## P0：固定数据契约和Mock接口

### 目标

固定模块边界，使真实模块与 Mock 可以直接替换。

### 实施步骤

1. 实现第 4 节的数据对象。
2. 定义 PriorityProvider、SLOProvider、HeavyRequestClassifier、BusyDetector、DelayScheduler、EndpointEnvironment、RoutingPolicy 和 TelemetryUpdater 接口。
3. 建立全局模拟时钟，算法中不直接读取机器当前时间。
4. 建立统一随机数管理器。
5. 每次运行生成 run_id，并保存完整解析后配置。

### 验证

- 数据对象可以序列化和反序列化；
- 同一输入、配置和 seed 得到相同 Mock 输出；

## P3：窗口、SLO、Pareto和评分组件实验

### 目标

独立证明窗口统计、衰减、先验、SLO、Pareto 和线性评分计算正确。

### 人工构造候选

至少包括：

1. 便宜但慢；
2. 昂贵但快；
3. 成本性能平衡；
4. 同时更贵且更慢的被支配点；
5. 样本很少、需要历史先验的 Endpoint。

### 实施步骤

1. 验证固定窗口和自适应窗口。
2. 验证指数衰减。
3. 验证近期样本与历史先验融合。
4. 验证 SLO 比率。
5. 构造 Pareto Frontier。
6. 归一化候选成本和性能。
7. 扫描 λ、η、ρ。
8. 对窗口和半衰期执行时间序列回放。

### Pareto维度

非流式：

```text
(cost, E2E / SLO_E2E)
```

流式：

```text
(cost, eta * TTFT / SLO_TTFT + (1 - eta) * TPOT / SLO_TPOT)
```

当前使用二维Pareto，与成本—综合性能图保持一致。先分别检查TTFT/TPOT硬SLO，再按η合成性能；η为0或1也不取消另一个指标的SLO约束。三维Pareto可作为后续设计选项，但本阶段不实现，不能混淆两种前沿。

流式评分：

```text
performance =
    eta * normalized_TTFT
  + (1 - eta) * normalized_TPOT

score =
    lambda * normalized_cost
  + (1 - lambda) * performance
```

### 成本模式

本阶段只实现单位价格成本。预计请求总费用仅列为后续可选扩展，不是当前可用配置：

```text
unit_price_cost =
    rho * input_price
  + (1 - rho) * output_price

estimated_request_cost =
    input_tokens / 1_000_000 * input_price
  + predicted_output_tokens / 1_000_000 * output_price
```

默认可继续使用单位价格。如果需要证明重型请求降低实际总费用，必须增加预计请求成本实验。

### 验证

- 被支配点进入 Pareto 次数为 0；
- λ 增大时总体更偏向低成本；
- λ 减小时总体更偏向低延迟；
- η 增大时流式选择更重视 TTFT；
- ρ 改变时输入、输出价格偏好符合预期；
- 衰减能更快响应近期性能突变；
- 样本少时使用先验，近期样本增加后先验影响下降；
- 无候选满足 SLO 时触发指定 fallback。

### 输出

- 组件测试报告；
- 参数扫描 CSV；
- 代表性 Pareto 图；
- 窗口预测误差、regret、排序准确率和切换率。

### 通过条件

所有人工用例的选择与预期一致，所有公式具有边界单元测试。

## P5：繁忙判断算法

### 目标

为每个候选模型—Endpoint组合输出状态、原因、余量和预计等待时间。

### Projected Load

```text
u_concurrency =
    (current_concurrency + 1) / max_concurrency

u_rpm =
    (current_rpm + 1) / max_rpm

u_tpm =
    (current_tpm + estimated_request_tokens) / max_tpm

capacity_pressure =
    max(u_concurrency, u_rpm, u_tpm)
```

estimated_request_tokens 的口径必须与相应 Endpoint 的 TPM 定义一致。

### 状态

| 状态        | 含义                        |
| --------- | ------------------------- |
| NORMAL    | 可立即执行                     |
| PRESSURED | 未超硬限制，但负载、排队、延迟或错误压力较高    |
| BLOCKED   | 预计超硬限制，或健康、Cooldown等不允许发送 |

### 滞回

- NORMAL 连续超过 enter_threshold 后进入 PRESSURED；
- PRESSURED 连续低于 exit_threshold 后恢复 NORMAL；
- enter_threshold 大于 exit_threshold；
- BLOCKED 解除必须同时满足容量、健康和Cooldown条件。

### 实施步骤

1. 实现 RPM、TPM和并发 projected load。
2. 加入预计队列等待。
3. 加入近期延迟膨胀。
4. 加入429、5xx和整体健康状态。
5. 实现进入、退出阈值和连续窗口。
6. 返回 busy_reason、headroom和retry_after。
7. 只有所有候选都不适合立即执行时，才进入延迟调度。

### 场景

- RPM阈值前后；
- TPM阈值前后；
- 并发阈值前后；
- 一个输入重型请求加入前后；
- 瞬时突发；
- 持续爬升；
- 429突增；
- 延迟上升但尚未超容量；
- Endpoint恢复；
- 阈值附近反复波动；
- 所有Endpoint繁忙；
- 部分Endpoint繁忙。

### 指标

- precision、recall；
- 误报率、漏报率；
- 检测延迟、恢复延迟；
- 状态抖动次数；
- 避免的429数量；
- 因过早判忙造成的闲置容量；
- 算法耗时。

### 输出

- busy_detector_case_report；
- 各场景状态时间线；
- 阈值扫描结果；
- 误报、漏报、抖动和检测延迟汇总；
- 每次判断的busy_reason与headroom明细。

### 通过条件

- 硬容量超限请求不被直接发送；
- 状态不在阈值附近高频切换；
- 突发和恢复在配置时间内被识别；
- 输出能解释具体繁忙原因。

## P7：延迟调度Mock

### 目标

在真实算法未完成时验证排队、优先级、deadline、aging和容量释放后的重新调度。

### 基本规则

1. 高优先级可以跳过批量聚合等待，但仍受硬容量限制。
2. 入队前必须已知 SLO、deadline和max_wait。
3. 同一基础优先级内可以偏向预计服务时间更短的请求。
4. 等待时间通过 aging 提升有效优先级。
5. deadline 即将到期的请求获得额外紧迫度。
6. 超过 max_wait 必须降级或失败，不能无限等待。

可使用下式作为 Mock，不将其当作最终算法：

```text
effective_priority =
    base_priority_weight
  + aging_weight * normalized_wait
  + deadline_weight * urgency
  - service_time_weight * normalized_service_time
```

### 验证

- 高优先级平均等待低于普通和低优先级；
- 高优先级不能突破硬容量；
- 同优先级短请求可以优先；
- 长请求通过 aging 最终执行；
- 请求不会超过max_wait而没有结果；
- 容量释放可以唤醒排队请求；
- 出队时重新读取状态并重新选路；
- 取消和超时不遗留状态。

### 指标

- 各优先级等待P50、P95、P99；
- 高优先级按时完成率；
- 最大等待时间；
- 饥饿率；
- 重型请求完成率；
- 调度吞吐和调度耗时。

### 输出

- scheduler_case_report；
- 请求入队、唤醒、出队和超时事件；
- 各优先级等待分布；
- 饥饿、公平性和deadline统计。

### 通过条件

预设顺序用例通过，低优先级和长请求饥饿率为0。

## P9：闭环场景与基线对照

### 基线

| 策略                    | 含义                      |
| --------------------- | ----------------------- |
| Random                | 从可用候选随机选择               |
| Round Robin           | 对候选轮询                   |
| Cheapest              | 选择最低成本                  |
| Fastest EWMA          | 选择近期估计延迟最低              |
| Least Loaded          | 选择 projected load 最低    |
| Static Weighted Score | 不做Pareto，仅固定加权          |
| Pareto Only           | Pareto路由，不含繁忙和延迟        |
| Pareto + Busy         | 加入繁忙，不含优先级和延迟           |
| Full Policy           | Pareto、繁忙、优先级、重型信息和延迟调度 |

所有策略必须使用：

- 相同硬过滤；
- 相同请求流和基础随机数；
- 独立但相同的初始状态；
- 相同重试上限；
- 相同数据可见范围。

### 场景

| 编号  | 场景           | 验证点       | 预期行为                |
| --- | ------------ | --------- | ------------------- |
| S1  | 稳态低负载        | 基础选路      | 基本无排队，选择符合λ偏好       |
| S2  | 成本性能冲突       | Pareto和评分 | λ增大时更偏向低成本          |
| S3  | 瞬时突发         | 繁忙和排队     | 减少429，控制尾延迟         |
| S4  | 持续高负载        | 稳定性       | 不抖动，不突破硬容量          |
| S5  | 输入重型集中       | TPM感知     | 选择TPM余量更充分的Endpoint |
| S6  | 输出重型流式       | TPOT与预计输出 | 偏向生成能力更强的Endpoint   |
| S7  | 分类重型         | 任务类型感知    | 选择该类任务表现更好的Endpoint |
| S8  | 混合优先级        | 优先级和公平性   | 高优先级按时率提升且无饥饿       |
| S9  | Endpoint逐渐变慢 | 窗口与衰减     | 逐步减少选择              |
| S10 | 持续429        | Cooldown  | 快速转移并避免反复探测         |
| S11 | Endpoint故障   | 故障切换      | 移出候选并受控重试           |
| S12 | Endpoint恢复   | 滞回恢复      | 逐渐恢复流量              |
| S13 | 冷启动或低样本      | 历史先验      | 先使用先验，近期样本逐步覆盖      |
| S14 | 所有Endpoint繁忙 | fallback  | 等待、降级或拒绝符合配置        |
| S15 | 流式与非流式混合     | 窗口隔离      | TTFT、TPOT与E2E不互相污染  |
| S16 | 性能排序反转       | 衰减敏感性     | 新趋势被及时识别            |

### 判断原则

不要求完整策略在所有指标上都第一。应判断：

- 是否在目标 SLO 和成本约束下优于或不劣于主要基线；
- 行为是否符合场景预期；
- 收益是否跨多个 seed 稳定；
- 改善是否确实来自目标模块。

### 输出

- 每个场景的逐策略原始指标；
- 按模型、流式类型、优先级和重型类别分组结果；
- 配对差值和95%置信区间；
- 场景级结论与不符合预期的案例；
- 代表性请求DecisionTrace和离线Pareto图。

### 通过条件

- 所有基线使用相同输入、初始状态和基础随机数；
- 策略之间不存在状态污染；
- 预定场景均完成或有明确跳过原因；
- 主要结论在多个seed下方向一致；
- 每个结论都能追溯到原始指标和DecisionTrace。

### 开销规模

| -------------- | ------------- |

## 9. 统计方法和公平比较

1. 所有策略使用同一批 CanonicalRequest。
2. 使用相同场景和基础随机数。
3. 每个策略从独立且相同的初始状态开始。
4. 随机实验先运行20个seed，若置信区间不稳定再增加。
5. 使用配对差值比较策略，不只比较两个独立平均值。
6. 报告均值、中位数、P95、P99和95%置信区间。
7. 明确区分 warm-up 与 measurement 区间。
8. 调参仅使用训练和校准段，测试段只运行最终参数。
9. 不因成本最低而忽略严重SLO违约，也不因延迟最低而忽略成本。
10. 被跳过的模型、模式和场景必须记录原因。

## 14. 阶段验收门

### Gate A：数据可信

完成 P0～P2：

- 数据契约稳定；
- 无未来信息泄漏；
- SLO、优先级和重型信息可复现；
- 字段缺失和样本不足透明。

### Gate B：选择算法正确

完成 P3：

- 指标计算正确；
- 被支配点不被选；
- 参数变化符合解释；
- SLO fallback明确。

### Gate C：环境和繁忙算法可信

完成 P4～P5：

- 模拟器容量守恒；
- 性能随负载按预期变化；
- 繁忙判断识别压力和恢复；
- 运行可复现。

### Gate D：闭环流程稳定

完成 P6～P8：

- Mock可替换；
- 所有分支可追踪；
- 无硬容量超卖和状态泄漏；
- 排队无饥饿。

### Gate E：策略结论可信

完成 P9～P10：

- 基线比较公平；
- 多seed结果稳定；
- 消融能够解释收益；
- 开销覆盖完整热路径。

## 15. 实验前必须确定的决策

1. 成本使用单位价格、预计请求总成本，还是两者均实验。
2. 无Endpoint满足SLO时，是等待、最小违约、降级、备用Endpoint还是拒绝。
3. 高优先级是否有预留容量以及比例。
4. Endpoint的TPM定义包含输入、输出还是二者。
5. priority、deadline和SLO如何映射。
6. classification-heavy的业务定义和标签来源。
7. 会话或前缀亲和性是硬约束还是软偏好；首轮若不验证建议关闭。
8. 重试是否重新选路，最大次数和总deadline如何约束。
9. 历史先验的生成区间和更新频率。
10. Endpoint恢复后是否采用逐步放量。

## 16. 整体完成标准

只有同时满足以下条件，才能认为实验体系完成：

- 能用一个命令运行指定场景和全部基线；
- 输入数据、配置、seed和代码版本完整记录；
- 每个请求产生可解释的DecisionTrace；
- 模拟环境形成闭环，选择会影响后续状态；
- 硬容量超卖次数为0；
- 每个流程分支都有自动测试；
- 报告包含总体、流式/非流式、优先级和重型类别分组；
- 至少完成一次多seed基线比较；
- 至少完成一次核心模块消融；
- 路由耗时不包含绘图和报告写入；
- 报告明确说明结论、适用范围和局限；
- 不把历史旧策略选择当作真实最优标签；
- 进入真实流量前另行进行Shadow Traffic或小流量A/B验证。
