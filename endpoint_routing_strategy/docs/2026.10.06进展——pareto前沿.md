# 一、数据方面做了什么

## 1. 原始数据是什么

原始流量日志是一条请求执行结束后的记录，包含：

- 请求 ID、用户 ID、目标模型、是否流式。
- 实际输入、输出 Token 数。
- 最终选择的 Endpoint。
- 成功失败、HTTP 状态码、完成耗时。
- 每次尝试的详细记录。
- ......

它能回答“这次请求最后发生了什么”，但不能直接作为“请求刚到达、还没选择 Endpoint”时的输入。

原因是：最终 Endpoint、实际输出长度、最终耗时等信息，在选路时尚不可知。直接使用这些字段会产生未来信息泄漏。

**把数据拆成了不同阶段**

## 2. 处理流程

### 第一步：清洗和标准化

检查数据的完整性和可用性

### 第二步：按时间划分数据

当前配置按时间先后划分为：

- 训练区间：约 60%。
- 校准区间：约 20%。
- 测试区间：约 20%。

训练画像只使用截止时间之前已经完成的结果。

这样可以保证：后面的请求使用的是当时已经可知的信息，而不是未来结果。

### 第三步：构造请求到达时的数据

由 `build_incoming_request()` 完成，保留：

- 请求、用户和模型标识。
- 到达时间。
- 流式类型。
- **预测输入、输出 Token**。
- 字段来源和数据追溯信息。

不把最终 Endpoint、HTTP 状态、最终耗时、实际输出长度带入选路输入。

### 第四步：补充调度画像

由 `enrich_request()` 完成，补充：

- 优先级。
- SLO 等级和具体阈值。
- 输入重型、输出重型等标记。
- 预计服务时间。
- 剩余时间余量和紧急程度。

## 4. 新增标签怎样计算

### 优先级

当前缺失优先级时，使用请求 ID 和固定种子的稳定哈希，按配置比例分配：

```
high：10%
normal：70%
low：20%
```

### 轻重请求

当前按预测长度判断：

```
输入重型阈值 = max(4096, 历史输入Token_P90)
输出重型阈值 = max(512, 历史输出Token_P90)
```

这只是 Token 阈值分类，还不是任务分工中的重型请求决策树。

### 预计服务时间和模拟 SLO

当前数据生成仍采用经验规则：

```
r_in  = 预测输入Token / 历史输入Token中位数
r_out = 预测输出Token / 历史输出Token中位数
```

非流式：

```
预计服务时间 =
历史E2E_P75 × max(0.25, 0.3×r_in + 0.7×r_out)
```

流式：

```
预计TTFT = 历史TTFT_P75 × sqrt(max(0.25, r_in))
预计TPOT = 历史TPOT_P75

预计服务时间 =
预计TTFT + max(预测输出Token−1, 0) × 预计TPOT
```

再分别乘以 1.5、2.0、3.0，生成三个等级的模拟阈值。

### 紧急程度

```
剩余预算 = 截止时间 − 当前时间
时间余量 = 剩余预算 − 预计剩余服务时间
余量比例 = 时间余量 / 原始SLO预算
```

流式还检查 TTFT，采用更紧的约束。

当前规则：

- 余量比例 ≤ 10%：`critical`。
- ≤ 30%：`elevated`。
- 其余：`normal`。

# 二、按照流程图，每一步目前怎样实现

## 1. 模型确定 → 请求到达

模型由上层确定，我们只负责选择 Endpoint，不负责模型选择。

首先将增强记录转换为正式请求对象，读取：

```
model_id、输出模式、预测长度、SLO、优先级及画像信息
```

## 2. 观测状态 → 硬过滤不可用 Endpoint

内存状态由 `InMemoryRoutingState` 统一维护，里面有两个类：

```
ModelEndpointRegistry：(model_id, endpoint_id)
→ 价格、容量、当前用量、启停、冷却、先验

ModelEndpointStateIndex：(model_id, endpoint_id, stream_type)
→ 近期性能记录（窗口）
```

通过模型索引直接找候选，不重新扫描全部日志。

硬容量检查使用：

```
预计RPM = 当前RPM + 1

预计TPM = 当前TPM
        + 预测输入Token
        + 预测输出Token

预计并发 = 当前并发 + 1
```

预计值超过该模型—Endpoint 的容量才排除，恰好等于上限可以通过。同时排除：

- 已禁用。
- 仍在冷却期。
- Endpoint 已标记不健康。
- 没有有效价格或必要性能证据。
- 成功率低于配置底线。

**上述基本过滤已实现。**

## 3. 请求优先级 → 是否繁忙

图中设计为：

```
高优先级 → 直接进入选路

普通/低优先级 → 判断是否繁忙
              ├─ 非繁忙：即时选路
              └─ 繁忙：聚合、排序、延迟调度
```

**这段优先级分流和繁忙判断目前未实现。**

当前所有请求都进入同一个即时选择器。优先级通过数据准备阶段的 SLO 设置间接影响约束，但没有实现高优先级跳过等待、普通请求入队等行为。

已实现的硬容量过滤不等于软繁忙判断：

- 硬过滤：超过限制，不能发。
- 软繁忙：尚未超限，但压力较高，可能需要延迟调度。

后者按当前要求暂缓。

## 4. 根据窗口统计历史信息

由 `compute_candidate()`、`select_window()` 完成。

默认窗口候选为：

```
5、15、30、60、180、360分钟
```

选择达到目标尝试样本数的最短窗口；全部不足时使用最大窗口，再检查指标证据是否足够，必要时融合先验。

样本时间权重：

$$
w_i = 2^{-\text{样本年龄}/\text{半衰期}}
$$

默认半衰期为 30 分钟。旧样本不是突然全部丢弃，而是逐渐降低影响。

对成功且具有有效指标的记录计算加权 P95。有效样本数：

$$
n_{\mathrm{eff}}=\frac{(\sum_i w_i)^2}{\sum_i w_i^2}
$$

逐指标融合先验：

$$
\alpha=\frac{\text{先验强度}}{n_{\mathrm{eff}}+\text{先验强度}}
$$

$$
\widehat{m}=(1-\alpha)P95_{\mathrm{近期}}+\alpha m_{\mathrm{先验}}
$$

近期有效样本越多，历史先验影响越小。

这一部分已实现，但属于指数时间加权统计，不是递推式 EWMA，也不是针对当前请求长度训练的 Endpoint 时延预测模型。

## 5. 区分流式、非流式 → 计算性能与成本

### 非流式性能

$$
P_e=\frac{\widehat{E2E}_e}{SLO_{E2E}}
$$

### 流式性能

$$
P_e=\eta\frac{\widehat{TTFT}_e}{SLO_{TTFT}} +(1-\eta)\frac{\widehat{TPOT}_e}{SLO_{TPOT}}
$$

其中 η 可配置：

- η 大：更重视首 Token。
- η 小：更重视持续生成速度。

数值越小，性能相对预算越好。

### 请求费用

先由 `resolve_request_price()` 根据预测输入长度匹配价格档，再计算：

$$
C_e= \frac{\widehat{T}_{in}p_{in,e} +\widehat{T}_{out}p_{out,e}}{10^6}
$$

这里使用预计请求费用，而不是仅比较每百万 Token 单价。

币种必须一致，目前不自动换汇。

**这些部分已实现。**

## 6. 检查 SLO → 构建 Pareto → 线性选择

**先明确请求类型、计算指标并过滤 SLO，再对可用集合构建 Pareto。**

否则，不符合 SLO 的点可能影响前沿判断。

### SLO 检查

设请求已经消耗时间为 (t)：

```
剩余E2E预算 = 原始E2E预算 − t
剩余TTFT预算 = 原始TTFT预算 − t
TPOT预算不扣开始前的等待时间
```

逐项判断：

```
E2E估计 ≤ 剩余E2E预算
TTFT估计 ≤ 剩余TTFT预算
TPOT估计 ≤ TPOT预算
```

非流式检查 E2E；流式检查 TTFT、TPOT。

### Pareto 判断

若 Endpoint j 满足：

$$
C_j\le C_i,\quad P_j\le P_i
$$

且至少一项严格更好，则 i 被支配，不能作为首选。

例如：

| Endpoint | 预计费用 | 性能值 | 是否在前沿 |
| -------- | ---- | --- | ----- |
| A        | 0.01 | 0.4 | 是     |
| B        | 0.02 | 0.2 | 是     |
| C        | 0.03 | 0.6 | 否     |

A、B 分别在成本、性能方面有优势；C 两方面都不如 A。

### 线性评分

$$
C'_e=\frac{C_e}{\text{可用候选正费用的中位数}}
$$

$$
Score_e=\lambda C'_e+(1-\lambda)P_e
$$

在前沿上选择最小分数：

- λ 越大越重成本。
- λ 越小越重性能。

这实现的是线性取舍和确定性选择。

## 7. 繁忙分支：聚合、分类、排序、选择 Endpoint 池

图中的这些节点尚未实现：

```
短时间聚合请求
→ 区分短/长或重型请求
→ 计算有效优先级
→ 窗口内的调度算法
→ 选路
```

当前状态是：

- 有优先级、轻重和紧急程度字段。
- 有 Token 阈值分类。
- 没有完整重型请求决策树。
- 没有有效优先级排序公式生效。
- 没有批量聚合、延迟队列、等待老化和防饥饿。
- 没有软繁忙 Endpoint 池。

因此，不应向甲方汇报为“调度分支已经跑通”。

## 8. 分发执行 → 失败切换

真实 HTTP 分发尚未接入，但候选计划和失败切换控制逻辑已实现。

默认输出：

```
一个首选 + 至多两个备用
```

首选依据成本、性能；备用从满足相同硬约束的剩余集合中按稳定性选择。备用不强制来自二维 Pareto，因为一个更贵、更慢的点可能更可靠。

稳定性使用近 60 分钟的加权成功率和有效样本量。设成功率为 p、证据样本量为 n，保守排序代理为：

$$
L= \frac{ p+\frac{z^2}{2n} -z\sqrt{\frac{p(1-p)}{n}+\frac{z^2}{4n^2}} }{ 1+\frac{z^2}{n} }
$$

默认 (z=1.96)。它用于降低小样本“100% 成功”的误导，不是经过校准的置信保证。

备用排序为：

```
L高 → 成功率高 → 有效证据多 → 线性评分低
```

由 `FailoverSession` 管理尝试：

1. 首选失败，接收结果并更新状态。
2. 排除已尝试 Endpoint。
3. 扣除已经耗掉的时间预算。
4. 重查备用的容量、健康、冷却和 SLO。
5. 按最新稳定性决定下一次尝试。

## 9. 更新运行状态 → 反馈下一次决策

图中三个反馈方向的进度不同：

| 反馈方向         | 当前情况                              |
| ------------ | --------------------------------- |
| 并发、RPM、TPM余量 | 有状态字段和更新接口；真实调用时的计数、占用、释放未接入      |
| 性能历史         | 已实现完成观测写入窗口；下一请求重新计算性能和前沿         |
| 失败、限流、恢复     | 已实现质量统计及失败会话冷却；真实健康探测、熔断恢复机制未完整实现 |

失败会话中：

- 429 按 Retry-After 或默认 30 秒设置组合冷却。
- 5xx 默认冷却 10 秒。
- 不缩短已经存在的更长冷却。
