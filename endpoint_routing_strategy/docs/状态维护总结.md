# Endpoint 路由状态维护总结

## 1. 总体结构

当前实现只使用内存，不在每次请求到达时扫描配置文件或历史数据文件。网关启动时建立索引，后续通过键直接读取：

```text
model_id
  -> 模型级路由策略

(model_id, endpoint_id)
  -> 模型与Endpoint组合的容量、当前用量、配置和运行状态

endpoint_id
  -> Endpoint整体负载、健康状态和支持模型

(model_id, endpoint_id, stream_type)
  -> 对应调用模式下的近期性能观测窗口
```

其中配置文件和历史文件只负责启动初始化、离线实验或冷启动先验。线上请求路径只遍历当前模型对应的候选 Endpoint。

### 轻量繁忙判断补充

`InMemoryRoutingState` 新增 `busy: BusyDetector`，通过 `state.assess_busy(model_id, at_time=..., endpoint_ids=...)` 显式调用。它复用组合的 RPM/TPM/并发计数，只额外保存繁忙记忆位和每个模型最近评估时间，不创建重复容量缓存。`catalog.capacity_snapshot()` 在同一把锁内读取当前模型的组合状态与 Endpoint 健康，避免丢失满载点或混读版本。

每个组合的压力为三项已知利用率最大值，默认达到 0.8 进入、三项容量已知且降至 0.6 或以下退出；零容量、禁用、故障、冷却归为不可用，未知容量不能证明空闲。模型汇总返回 `idle/busy/unknown/unavailable`，保留局部繁忙集合；存在已知低压力替代时不判整个模型繁忙。可以传入已筛选 Endpoint 子集，但本模块不自行检查 SLO/价格/预测长度，不预占容量、不变更选路评分。详见 [繁忙判断说明](繁忙判断说明.md)。

### 请求感知入口与失败切换说明

`RoutingEngine.route_request()` 使用初始请求中的预测输入/输出Token与请求级SLO。容量检查比较的是 `current_rpm+1`、`current_tpm+预测输入+预测输出`、`current_concurrency+1` 与组合上限，恰好等于上限允许，超过时排除；零上限不可用，未知上限可通过 `unknown_capacity_policy=allow/block` 指定处理。

新入口保留在线P95，同时新增逐指标先验融合估计 `estimated_e2e_ms/estimated_ttft_ms/estimated_tpot_ms`、`metric_prior_weights`、`metric_effective_samples`，严格SLO检查使用融合估计。请求已等待时扣减E2E/TTFT预算。模型策略SLO是旧入口默认值，新入口使用请求级SLO，λ/η/ρ仍取模型配置或显式覆盖。

默认成本现为预测长度乘价格后的预计请求费用，ρ 不参与真实预计账单；旧单位价格与偏好加权费用需显式选择。Token 价格档默认按预测输入匹配唯一档，不自动换汇。首选是二维 Pareto 上的最小评分点，默认加至多两个稳定备用，备用仍需满足全部硬约束。

决策记录包含容量投影、价格档解析、费用分项、稳定性、排除原因、SLO 比率、Pareto 和评分、推荐位置及计时。`route_request()` 本身不修改负载、不执行请求；`no_candidate` 返回分类原因。`FailoverSession.complete_attempt()` 则会写入完成观测，429/5xx 按重试策略设置组合冷却。单独调用 `record_observation()` 只更新窗口/质量，不自动冷却。详见 [逐步流程与选择策略说明](../experiments/selection/README.md)。

## 2. 模型级状态：`model_id -> ModelRoutingPolicy`

这类状态描述“某个模型应该按照什么目标和偏好进行路由”。

| 字段                | 含义                       | 获取或维护方式         | 路由用途                        |
| ----------------- | ------------------------ | --------------- | --------------------------- |
| `model_id`        | 模型唯一标识                   | 来自配置或网关请求中的目标模型 | 作为策略索引键                     |
| `slo_e2e_ms`      | 非流式端到端时延目标，单位毫秒          | 人工配置，默认 60000   | 将非流式 P95 E2E 转换为相对 SLO 的性能值 |
| `slo_ttft_ms`     | 流式首 Token 时延目标，单位毫秒      | 人工配置，默认 5000    | 归一化 TTFT                    |
| `slo_tpot_ms`     | 流式平均每个后续 Token 时延目标，单位毫秒 | 人工配置，默认 100     | 归一化 TPOT                    |
| `lambda_cost`     | 成本偏好 λ，范围 0～1            | 人工配置            | 最终评分中成本所占权重；越大越偏向低价         |
| `eta_ttft`        | TTFT 偏好 η，范围 0～1         | 人工配置            | 流式性能中 TTFT 所占权重；剩余权重属于 TPOT |
| `rho_input_price` | 输入价格偏好 ρ，范围 0～1 | 人工配置 | 仅单位价格或偏好加权模式有效；默认真实预计费用不使用 |
| `cost_mode` | 评分成本目标 | 默认 `predicted_request` | 预计请求费用；可显式改 `weighted_predicted_request` 或 `unit_price` |
| `top_k` | 推荐 Endpoint 总数上限 | 默认 3，正整数 | 含首选，不足则返回更短列表 |
| `backup_pool` | 备用候选池 | 默认 `all_feasible`，可改 `pareto` | 默认允许成本/性能被支配但稳定的可用点作备用 |
| `stability_z` | 保守稳定性排序参数 | 默认 1.96，有限正数 | 控制 Wilson 式下界代理的谨慎程度，不是成功率保证 |

维护接口为 `state.policies.upsert(policy)`、`get(model_id)` 和 `remove(model_id)`。写入时校验权重、SLO、费用模式、Top K 和稳定性参数。请求入口以请求 SLO 为准，模型 SLO 是旧接口默认值。

## 3. 模型—Endpoint 状态：`(model_id, endpoint_id) -> ModelEndpointRuntimeState`

这类状态描述“某个 Endpoint 为某个模型提供服务时”的价格、容量、可靠性和可用性。相同 Endpoint 为不同模型服务时，可以拥有不同价格档和容量。

| 字段                      | 含义                             | 获取或计算方式                                                                     | 路由用途                             |
| ----------------------- | ------------------------------ | --------------------------------------------------------------------------- | -------------------------------- |
| `model_id`              | 模型标识                           | Endpoint 配置文件中的模型列表                                                         | 组合索引键之一                          |
| `endpoint_id`           | Endpoint 标识                    | Endpoint 配置文件                                                               | 组合索引键之一                          |
| `price_tier_index` | 配置的价格档序号 | 默认 0；通过 `set_price_tier()` 修改 | 没有 Token 档条件时的默认档或显式配置档；新入口可按预测输入匹配不同档 |
| `capacity_rpm`          | 该组合每分钟最大请求数                    | 初始化时读取该模型的 `capacity_config.rpm`                                            | 与该组合的 `current_rpm` 比较           |
| `capacity_tpm`          | 该组合每分钟最大 Token 数               | 初始化时读取该模型的 `capacity_config.tpm`                                            | 与该组合的 `current_tpm` 比较           |
| `capacity_concurrency`  | 该组合最大并发数                       | 初始化时读取该模型的 `capacity_config.concurrency`                                    | 与该组合的 `current_concurrency` 比较   |
| `current_rpm` | 组合一分钟请求量 | 网关维护滑动计数器并通过 `update_model_endpoint_load()` 更新 | 检查 `current_rpm+1` 是否超过上限 |
| `current_tpm` | 组合一分钟 Token 用量 | 网关维护 Token 滑动计数器并更新 | 检查加入预测输入+输出 Token 后是否超过上限 |
| `current_concurrency` | 组合已占用并发数 | 调用方在请求开始/结束时更新 | 检查 `current_concurrency+1` 是否超过上限 |
| `historical_prior`      | 历史性能先验                         | 从请求引用的 3 天和 7 天快照构造，也可由网关直接设置                                               | 小窗口样本不足时稳定性能和成功率估计               |
| `enabled`               | 该组合是否启用                        | 默认 `True`；通过 `set_enabled()` 修改                                             | 为 `False` 时不进入候选集                |
| `cooldown_until`        | 冷却截止时间                         | 由限流、熔断或失败处理逻辑调用 `set_cooldown()` 设置                                         | 截止时间之前不进入候选集                     |
| `success_rate`          | 近期成功率                          | 最近健康窗口内 `success=True` 的次数除以总尝试数                                            | 记录可靠性，可作为路由可行性判断依据               |
| `rate_limit_429_rate`   | 近期 HTTP 429 比例                 | 最近健康窗口内 429 次数除以总尝试数                                                        | 判断限流风险、触发 Cooldown 的依据           |
| `server_error_5xx_rate` | 近期 HTTP 5xx 比例                 | 最近健康窗口内 5xx 次数除以总尝试数                                                        | 判断服务端故障风险、触发降级的依据                |
| `health_sample_count`   | 上述质量比例的样本数                     | 最近健康窗口内的尝试总数                                                                | 判断质量比例的可信程度                      |
| `updated_at`            | 最近更新时间                         | 每次修改组合运行状态时自动写入当前时间                                                         | 状态新鲜度检查和排障                       |

### 价格信息的保存方式

完整的 `price_config` 保存在 `EndpointOffering` 中，运行状态只保存当前 `price_tier_index`。读取价格时需要同时满足：

1. `pricing_status == "configured"`；
2. 根据 `pricing.py::resolve_request_price()` 得到唯一匹配 Token 档，或在无 Token 条件时使用有效配置档；
3. `billing_unit == "per_million_tokens"`；
4. 价格档货币与路由指定货币一致；
5. 输入、输出每百万 Token 单价均为非负有限值。

Token 档歧义、无匹配或未知 Token 条件不会猜测最低价。非 Token 条件（模态、时间等）须由调用方配置。`price_tier_mode="configured"` 也需通过所选档的 Token 条件校验。选档是请求级结果，不在每次路由时修改常驻的 `price_tier_index`。

当前系统不会自动换算人民币和美元。货币不一致的 Endpoint 会被排除，避免隐式汇率造成不可解释的成本比较。

### 历史先验的构造

当前离线加载逻辑读取请求所引用的 3 天和 7 天历史快照，并按照 `0.7 × 3天 + 0.3 × 7天` 合并以下信息：

- P95 成功请求时延；
- P95 流式首响应时延；
- 输出 TPS，并转换为 `TPOT代理值 = 1000 / TPS`；
- 成功率；
- 快照样本数。

历史快照不是每次路由的必需数据。生产环境可以只维护近期窗口；历史先验主要用于启动初期、低流量 Endpoint 或窗口样本不足的情况。

### 组合负载的更新方式

组合当前用量可以一次性刷新：

```python
state.catalog.update_model_endpoint_load(
    model_id,
    endpoint_id,
    current_concurrency=3,
    current_rpm=50,
    current_tpm=10000,
)
```

并发数提供加锁增减接口 `adjust_model_endpoint_concurrency(model_id, endpoint_id, +1/-1)`，但这不是对 RPM/TPM/并发同时进行的原子“检查并预占”。实际网关接入仍需负责调用前占用和完成后释放；选择器及失败规划器不自动增减用量。不同模型即使共用 Endpoint，其组合用量也分别维护。

## 4. Endpoint 整体观测状态：`endpoint_id -> EndpointRuntimeState`

这类状态描述 Endpoint 整体情况，不区分模型。为兼容和整体监控仍然保留，但聚合负载不作为某个模型是否达到容量的判断依据。

| 字段                    | 含义                  | 获取或维护方式                                 | 路由用途                                       |
| --------------------- | ------------------- | --------------------------------------- | ------------------------------------------ |
| `endpoint_id`         | Endpoint 唯一标识       | 配置文件或网关注册操作                             | 索引键                                        |
| `current_concurrency` | Endpoint 聚合并发观测值    | 可由监控系统更新                                | 仅用于整体监控，不参与组合容量判断                          |
| `current_rpm`         | Endpoint 聚合 RPM 观测值 | 可由监控系统更新                                | 仅用于整体监控，不参与组合容量判断                          |
| `current_tpm`         | Endpoint 聚合 TPM 观测值 | 可由监控系统更新                                | 仅用于整体监控，不参与组合容量判断                          |
| `health_status`       | Endpoint 整体健康状态     | 由健康检查、熔断器或运维系统更新，默认 `unknown`           | `unhealthy`、`down`、`disabled` 时排除 Endpoint |
| `supported_models`    | 当前 Endpoint 支持的模型集合 | 注册、更新或删除 `EndpointOffering` 时自动根据反向索引生成 | 查询某 Endpoint 能提供哪些模型，也用于配置同步               |
| `updated_at`          | 最近更新时间              | 更新负载、健康或支持模型集合时自动写入                     | 判断负载和健康数据是否过期                              |

Endpoint 聚合字段不从离线历史数据自动推算，通过 `update_endpoint_runtime()` 更新。聚合 RPM、TPM 和并发只用于观测；整体 `health_status` 仍可用于排除已确认不可用的 Endpoint。

## 5. 近期性能窗口：`(model_id, endpoint_id, stream_type) -> deque[Observation]`

每个模型、Endpoint 和请求类型分别维护一个有界队列。流式与非流式不会混在同一个性能窗口中。

### 单条观测字段

| 字段            | 含义             | 获取或计算方式                                               |
| ------------- | -------------- | ----------------------------------------------------- |
| `occurred_at` | 结果已可见的完成时刻 | 数据层使用尝试 `finished_at`；失败反馈使用报告结果的完成时刻，不能用到达时刻提前泄漏结果 |
| `endpoint_id` | 实际尝试的 Endpoint | 请求尝试记录                                                |
| `is_stream`   | 是否流式           | 请求参数                                                  |
| `success` | 尝试是否成功 | 历史数据清洗按日志结果判断；在线由调用方 `AttemptResult.success` 明确报告并校验结果一致性 |
| `result`      | 尝试结果文本         | 尝试记录，例如 success、error 等                               |
| `http_status` | HTTP 状态码       | Endpoint 响应                                           |
| `e2e_ms`      | 尝试级端到端时延       | 成功且完整计时可用时，`finished_at_ms - sent_at_ms`              |
| `ttft_ms`     | 首 Token 时延     | 流式、成功且完整计时可用时读取 `first_token_at_ms`                   |
| `tpot_ms`     | 后续 Token 平均时延  | `(E2E - TTFT) / (output_tokens - 1)`，要求输出 Token 数大于 1 |

### 窗口约束

- 默认每个键最多保留最近 360 分钟；可以在创建状态对象时调整。
- 每个键最多保留 20000 条观测，避免单个高流量组合无限占用内存。
- 新观测通过 `record_observation()` 增量写入。
- 删除模型—Endpoint 组合时，会同步删除该组合的流式和非流式窗口。
- 路由计算只读取所需键，不扫描其他模型、Endpoint 或请求类型。

### 质量统计与性能统计的区别

- 性能统计严格区分 `stream_type`，因为流式使用 TTFT/TPOT，非流式使用 E2E。
- 成功率、429率和5xx率当前合并同一模型—Endpoint下的流式与非流式观测，默认统计最近 60 分钟。
- 状态层保存上述不加权比例；备用排序另在决策时计算指数加权成功率、有效样本与保守下界代理，不将两种统计口径混用。

## 6. 候选 Endpoint 的形成过程

一次请求的模型已经确定后，系统按以下顺序取得候选：

1. 通过 `model_id` 直接读取该模型的 Endpoint 映射；
2. 排除 `enabled=False` 的组合；
3. 排除仍处于 Cooldown 的组合；
4. 排除整体健康状态为 `unhealthy/down/disabled` 的 Endpoint；
5. 比较该组合加入本请求后的预计并发/RPM/TPM与容量，超过上限才排除；
6. 根据预测输入解析价格档，验证计费单位和指定币种，计算本次预计费用；
7. 读取对应模式近期窗口与先验计算逐指标性能，同时读取组合两种模式近 60 分钟估计备用稳定性；
8. 对各 SLO 分别检查，E2E/TTFT 扣减已耗时预算；
9. 可用点中做二维 Pareto 和线性评分选首选，再按稳定性选至多 `top_k-1` 个备用；
10. 失败切换时用最新时间与状态重查上述约束，排除已经尝试的 Endpoint。

因此请求阶段不会遍历所有模型，也不会重新读取三份 JSONL 文件。实际遍历范围只是当前模型能够使用的 Endpoint 数量。

## 7. 更新来源汇总

| 更新场景                          | 应更新的状态                                                  |
| ----------------------------- | ------------------------------------------------------- |
| 网关新增模型—Endpoint 映射            | `register_endpoint(EndpointOffering)`                   |
| 删除映射                          | `remove_endpoint(model_id, endpoint_id)`，同时清理性能窗口       |
| 修改模型的 SLO 或 λ/η/ρ             | `policies.upsert(ModelRoutingPolicy)`                   |
| 调整价格档                         | `catalog.set_price_tier()`                              |
| 临时停用组合                        | `catalog.set_enabled()`                                 |
| 429、5xx或上层熔断后冷却 | `FailoverSession.complete_attempt()` 按策略设置，或上层调用 `catalog.set_cooldown()` |
| 新调用完成                         | `record_observation()`，自动写入窗口并刷新质量比例                    |
| 某模型在某 Endpoint 的 RPM/TPM/并发变化 | `catalog.update_model_endpoint_load()`                  |
| 某组合请求开始或结束                    | `catalog.adjust_model_endpoint_concurrency(..., +1/-1)` |
| Endpoint 聚合监控值或整体健康变化         | `catalog.update_endpoint_runtime()`；聚合负载不参与容量判断         |
| 冷启动历史数据到达                     | `catalog.set_prior()`                                   |

## 8. 请求级决策结构：`RoutingDecision` / `Candidate`

这不是新增常驻索引。每个请求根据当前状态即时计算，可记录到实验结果或网关审计日志。

| 字段组 | 关键字段 | 用途与计算 |
| --- | --- | --- |
| 请求输入 | 预测输入/输出 Token、请求 SLO、优先级/画像来源 | Token 用于费用/档位/TPM；SLO 用于硬检查及性能比例；轻重/紧急目前不直接加分 |
| 预计费用 | `estimated_input_cost/output_cost/request_cost`、`cost_mode`、`cost_raw` | 长度乘百万 Token 单价再除 100 万；真实预计账单与偏好目标分开保留 |
| 性能证据 | 在线 P95、`estimated_*_ms`、`metric_effective_samples`、`metric_prior_weights` | 时间衰减窗口与先验按指标融合，不是按请求长度训练的时延预测器 |
| 备用稳定性 | `stability_success_rate`、`stability_sample_count`、`stability_lower_bound`、429/5xx比例、来源 | 组合两种模式近 60 分钟加权成功与有限先验；下界是排序代理而非校准置信保证 |
| 约束/评分 | `feasible`、`exclusion_reason`、`pareto`、`score`、`routing_score` | `score` 仅前沿点；所有可用点另有 `routing_score` 用于备用破平 |
| 推荐计划 | `selected_endpoint`、`ordered_endpoints`、`backup_endpoints`、`route_rank/role` | 默认首选+至多两备用；备用不可绕过容量、健康、冷却或 SLO |
| 审计 | `endpoint_checks`、价格档解析、SLO/容量投影、阶段耗时 | 解释为什么选或不选，保存决策依据 |

## 9. 单请求失败会话：`FailoverSession`

会话记录初始计划 `route_plan`、已尝试列表 `attempts`、当前阶段 `status/stop_reason` 和累计预计费用。`RetryPolicy` 维护最大尝试数（含首选）、可重试错误、429/5xx 冷却和可选累计费用上限。

`next_attempt()` 重查最新状态和剩余 SLO，在初始推荐列表中选择尚未尝试的 Endpoint，重试阶段稳定性优先；`complete_attempt()` 写完成观测、更新冷却并决定继续/停止。`retry_safe=False` 默认不切换；已经向客户端输出内容也不切换。稳定优先候选超过累计预计费用上限时停止，不再搜索廉价备用。费用累加是完整预测尝试费用之和，不是实际失败账单。

该会话不发送 HTTP、不预占/释放容量、不实现软繁忙或延迟队列。真实调用、时间源、结果测量与负载计数由网关接入负责。

目前所有状态在进程重启后都会丢失。`ModelEndpointRepository` 只定义了未来数据库适配接口；后续可以增加数据库作为配置和先验的持久化来源，同时继续保留这些内存索引作为请求热路径。
