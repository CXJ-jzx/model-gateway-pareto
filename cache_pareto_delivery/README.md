## 2. 一条请求的完整策略流程

```text
上游确定模型，提供 messages、SLO、候选 Endpoint 的预计时延和预计费用
  → 消息精确编码 → 前缀树检索历史位置
  → 按原始 SLO（1.0 倍）筛选候选 → 计算 Pareto 和线性分数
  → 有合格前缀：最长前缀优先；否则：Pareto 排序
  → 返回首选及最多 3 个候选、选择原因
  → 调用 LiteLLM，检查真正执行的 Endpoint、响应及答案
  → 成功完成后写回前缀位置 → 用真实 usage／供应商金额核算费用
```

| 阶段 | 文件／函数 | 作用及输出 |
|---|---|---|
| 构造实验请求 | `experiment.document()`、`followup()` | 首次发送文档；后续复用文档查询不同字段 |
| 准备事前候选 | `supplier_experiment.run_supplier()` | 候选时延、预计 tokens 费用、SLO；本次结果不用于本次决策 |
| 编码消息 | `routing.prompt_key()` | 逐消息确定性 JSON 字节序列，保留角色、内容、空白及 options |
| 找历史位置 | `PrefixIndex.lookup()` | 返回实际记录过的前缀位置、匹配字节数和证据年龄 |
| 准入与排序 | `pareto_rank()` | 排除预计时延超过 SLO／估计缺失的候选，计算支配关系和线性分数 |
| 选择 | `CacheAwareRouter.choose()` | 返回 `selected_endpoint`、`ranked_endpoint_ids`、`reason` 及计算耗时 |
| 真实执行 | `experiment.run()` 内部 `call()` | `POST /v1/chat/completions`，使用 `metadata.endpoint_priority` 定向选路并核验 |
| 写回 | `CacheAwareRouter.feedback()` → `observe()` | 仅成功且身份确认后记录位置；在途、失败不写入 |
| 核算 | `supplier_experiment.supplier_fee()` | 官方按真实 tokens 和公开价；360 按 `usage.amount`；未知不当成零 |
| 汇总 | `supplier_experiment.report()` | 包括首次请求费用，分别统计成本、正确率和纯时延 SLO |

### 选择规则及公式

先进行严格准入：`estimated_e2e_ms <= slo_ms`，不使用 1.1／1.2 倍放宽。

`score = α × estimated_cost / median_positive_eligible_cost + (1−α) × estimated_e2e_ms / slo_ms`

- 两个目标均为越小越好；不存在另一合格点同时更便宜且更快时，该点在 Pareto 前沿。
- 有合格前缀：最长匹配优先，同长度多个位置按上述分数选择。这个 Endpoint 可以被支配，不要求它属于前沿。
- 没有合格前缀：前沿优先，按分数排序；有空位时用被支配的合格点补位。最终至多 3 个。
- 全部不合格：首选为 `None`，候选为空，不强行发请求。
- 返回候选次序不等于已经实现自动失败重试；真实调用器此次禁用重试。

### 前缀树怎样维护

`PrefixIndex` 使用压缩字节 Radix Tree。节点仅包含 `edge`（整段边）、`children`（下一字节索引）、`endpoints`（位置及完成时间）。只在完整处理过的输入末端记录证据，不将内部公共分叉当作缓存。

- 隔离键：`(可信 scope, model/version)`；不会跨租户或模型盲目复用。
- 默认证据 TTL：300 秒；位置上限：512；单条前缀上限：256,000 字节。
- `OrderedDict` 维护 LRU；最小堆维护过期事件，过期／刷新后会清理、压缩节点和堆。
- 查询不刷新 TTL，成功完成反馈才刷新；单进程内存，重启即失去位置证据。
- 是消息边界的精确匹配，不是语义匹配，不重建供应商 tokenizer／KV 块。
- **位置证据 ≠ 确认缓存命中；本地 TTL ≠ 供应商承诺的缓存寿命。**

### 调用方必须提供什么

```python
from routing import CacheAwareRouter

router = CacheAwareRouter()  # 常驻对象，不要每次请求重新创建
messages = [{"role": "user", "content": "同一份业务文档"}]
decision = router.choose(
    scope="tenant-a", model="model/version", messages=messages,
    candidates=[
        {"endpoint_id": "official", "estimated_e2e_ms": 800, "estimated_cost": 0.002},
        {"endpoint_id": "other", "estimated_e2e_ms": 2000, "estimated_cost": 0.001},
    ],
    slo_ms=5000, now_ms=0, alpha=0.8,
)
# 先检查 decision["selected_endpoint"] 是否为 None；再由网关真实执行。
# 只有真实完成并确认端点身份后，才调用：
# router.feedback(scope="tenant-a", model="model/version", messages=messages,
#                 endpoint=actual_endpoint, now_ms=completed_monotonic_ms,
#                 success=True, identity_verified=True)
```

`now_ms` 应由同一个单调时钟产生；上例的 0 仅展示接口。预计费用须使用同一币种／单位。标准估计为预测输入×输入价＋预测输出×输出价；未知缓存命中不能提前当成已确认折扣。

## 4. 本轮真实实验：怎么做的

实验日期 2026-10-20，经过已有 LiteLLM 的 4000 入口调用真实官方和 360；没有使用 Mos 的 4001 入口，没有改共享配置、价格或延迟。

| 项目 | 设计 |
|---|---|
| 场景 | 非流式、重复上下文、短回答 |
| 请求内容 | 虚构库存文档；先只回复 READY，再查询 item_0001／0002／0003 的 stock |
| 短／长输入 | 96／384 行；实际约 2,450／9,650 tokens |
| 输出 | 上限 64 tokens；本轮实际均 2 tokens |
| 执行参数 | 温度 0、关闭思考、自动重试 0、禁用网关完整响应缓存 |
| 分组 | 2 种历史位置×2 种长度×3 份独立文档＝12 组 |
| 每组 | 两种策略各自首次请求 1 次，后续查询 3 次；首次请求计费 |
| 公共前置观测 | 官方／360×短／长各一次，共 4 次；冻结为本轮时延估计 |
| 总量 | 4＋12×2×4＝100 次真实调用；每策略 36 条后续查询 |
| 规则 | α=0.8，SLO=5 秒；调用前固定，不按结果调整 |
| 控制 | 正文相同、早期标识不同，交替执行顺序；文档顺序固定随机打乱 |

后续请求为原 system＋完整文档＋实际 READY＋新问题，三条查询各自使用该结构，不逐轮无限累积会话。每条都能由文档自动查出唯一正确答案。

实验输入预测是消息文本长度的粗估（JSON 字符数除以 3）；预测输出为 2。结算使用真实 usage，不用粗估值。时延估计只有每个端点每种长度一次观测，不冒充充分的近期统计窗口。

## 5. 真实结果及费用口径

全部 100 次调用正确有效，完成 12／12 组；以下时延、达标率仅针对每策略 36 条后续查询。

| 总体指标 | 原 Pareto | 前缀优先＋Pareto |
|---|---:|---:|
| 首次请求＋后续调用数 | 48 | 48 |
| 后续答案正确／5秒达标 | 36/36；36/36 | 36/36；36/36 |
| 平均／最大响应时间 | 0.707／1.279秒 | 1.480／3.090秒 |
| 后续端点选择 | 官方36 | 官方18、360共18 |
| 首次请求费用估算 | 0.10175880 | 0.10180920 |
| 后续查询费用估算 | 0.04562880 | 0.03538008 |
| **含首次请求总费用估算** | **0.14738760** | **0.13718928** |

总体降本 **6.92%**，仅后续查询降本 **22.46%**。4 次公共前置观测另花费估算 0.03393680；两组均分后总成本为 0.16435600 对 0.15415768，降本 **6.21%**。三个比例不能混用。

| 历史位置／输入 | 原总费用估算 | 前缀总费用估算 | 变化 | 原／前缀平均响应 |
|---|---:|---:|---:|---:|
| 官方／短 | 0.00933972 | 0.00937572 | 增加0.39% | 0.743／0.740秒 |
| 官方／长 | 0.03251796 | 0.03255396 | 增加0.11% | 0.693／0.854秒 |

| 360／长 | 0.08353104 | 0.07394148 | 降低11.48% | 0.680／2.390秒 |

收益主要来自保留 360 已有上下文，尤其是长输入；官方历史位置两组都选官方，无额外路由收益，微小增费来自独立标识的 tokens 差异。前缀策略变慢主要因为选了较慢的 360，不是树检索：查树平均 0.059 毫秒，总决策 0.204 毫秒；原决策 0.142 毫秒。HTTP 响应计时不含路由计算。

### 费用证据与限制

- 官方：真实 `prompt_tokens`、命中 tokens、`completion_tokens` 乘实验当日公开闲时价，分别为输入1、缓存读取0.02、输出4元／百万tokens。
- 360：使用 `usage.amount`。12次首次冷请求与渠道普通公开价一致，支持CNY单位推断，但未认证到账单。
- 不使用 LiteLLM 用户侧 `response-cost` 充当采购成本；缺失采购费用保持未知。
- 360 的 hit／miss 均0但输入非0，不满足计数关系，不能据此断言缓存未命中；其18条后续费用仍可按 amount 记录。
- 原 Pareto 后续官方36次中30次明确命中、6次未命中；前缀组官方18次均明确命中，360的18次缓存计数未知。
- 其他两家在调用前因缓存采购计费依据不完整排除，不能将本轮收益外推至四家。
- 5秒是实验预算，不是完成业务校准的SLO；只有12个独立文档对、每份3次查询，且全为短回答，不声称生产统计显著性。
- 模型版本不同，库存提取正确不代表综合质量相同。尚未实现命中概率、供应商真实缓存寿命及剩余会话次数预测。

## 6. 后续如何使用

日常接入只需 `routing.py` 的 `choose()` 和 `feedback()`，由宿主系统提供真实 SLO、模型候选、统一费用和预计性能。不要把实验的 5 秒、一次观测估计和库存任务当成生产规则。

核对已存实验无需联网，运行第3节即可。若确实需要重新发真实请求，才安装：

```powershell
python -m pip install -r requirements.txt
```

现有真实入口为 `experiment.py --suite supplier-cost`，需显式提供 `--max-calls 100 --max-cost 1.2 --slo-ms 5000`，并配置可访问网关的 config／env 路径，或在已核验SSH主机密钥后使用 `--ssh`。脚本不会替你部署网关，默认旧服务器路径不是通用配置。

**不要直接照旧日期重跑费用实验**：`supplier_experiment.quote()` 对官方费率日历限定2026-10-20，其他日期必须先核对公开费率、峰谷和节假日规则。真实实验会产生费用；本次整理没有发新请求。
